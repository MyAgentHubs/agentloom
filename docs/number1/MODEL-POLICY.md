# #1 模型、推理档位与预算约定

本约定由维护者批准，适用于本任务分支后续的 Codex/其他 LLM 执行，包括协调者、实现者和 reviewer。它是模型与预算规则的唯一说明来源；graph.json 保存节点默认值，精确子单可收紧预算，不能自行放宽。不追改已完成工作的历史用量记录。

## 按工作选择模型

| 工作 | 默认模型 | reasoning_effort | 权限 |
|---|---|---|---|
| 文件搬迁、逐句注释翻译、台账、机械白名单更新 | gpt-5.6-terra | medium | 在已领取子单范围内执行 |
| 函数提取、参数调整、守卫迁移、回归测试 | gpt-5.6-sol | medium | 在已领取子单范围内执行 |
| 普通规划、协调、独立代码审查 | gpt-5.6-sol | medium | 仅加载当前节点与直接证据 |
| 锁、事务、Drop、终态顺序等复杂问题 | gpt-5.6-sol | high | 维护者事先批准该节点及阶段 |
| Sol 仍无法解决且有明确证据的难点 | gpt-6-astra | medium 或 high | 维护者专项批准该节点及阶段 |

纯机械子单可按本表使用 Terra；一旦包含语义判断或守卫修复，应在执行前按表标明 Sol。父 epic 的 Sol 默认值用于规划，不代表其所有机械子单必须使用 Sol。复杂问题不意味着必须升级；Sol medium 足以完成时维持原配置。

不默认使用 Astra，不默认使用 high；xhigh、max、ultra 等最高档不在常规授权范围。不能为了便宜把所有工作压到最低 effort；比较的是通过验收所需的总成本，包括失败、返工和审查。本表是项目调度约定，不保证某模型必然胜任每张单。

## Codex 执行与升级

1. 每次执行必须明确记录模型 ID 和 effort，包括子代理。CLI 显式传模型/推理配置；桌面端确认当前任务设置。不要继承未知全局默认，不修改贡献者全局配置，不带入旧会话的绕过 sandbox 参数。
2. graph 的 worker 是实现/规划默认值；独立 reviewer 默认 Sol medium，必须使用独立上下文读取实际 diff、测试和失败证据。同模型可以独立审查，不能把作者自查写成独立审查。
3. 失败先核环境、缩小任务、验证假设。失败次数、文件很大或“需要更聪明”不能自动授权升级。
4. 升级申请记录：节点 ID、失败复现、已排除原因、拟升级模型/effort、限定阶段、剩余预算和成功条件。维护者批准后只在该阶段使用，结束恢复默认；预算不得自动重置。
5. 模型或档位不可用时，暂停依赖该配置的执行。贡献者提交实际可用组合，由维护者一次性确认替代映射及适用范围；后续在同一批准范围复用，不逐单重问，也不默默改用更昂贵模型。新模型或范围变化需重新确认。
6. PR/节点状态记录实际配置和批准引用。声明只是审计证据；Markdown 与 JSON 本身不能强制控制 Codex 用量或验证模型身份。

## 共享预算与停止条件

- 一个可执行子节点默认最多 **3 轮 / 60 分钟 / 24,000 tokens**，先到任一上限即停止。更小子单已有较低预算时取较低值。
- 预算包含该节点的规划、实现、子代理、独立审查和返工；不能给每个角色再分一份完整预算。换模型、重开任务、重试和续跑不清零。
- 一轮是一次“观察/计划 → 修改 → 验收/审查”的尝试；返工进入下一轮。测试命令运行时间计入节点时间。
- 每批最多 **2 个并发 worker/reviewer，合计 80,000 tokens**；协调者的模型调用计入批次总量，节点仍受自己的较低上限约束。同组件共享文件的节点串行。
- 连续两轮同一失败且没有新证据，或任一预算耗尽：保存精确 diff、失败日志和下一步，停止并交维护者裁决；不能升级模型来绕过停止条件。
- 用量按工具实际报告统计，保留各次调用，不把已经包含在输出中的 reasoning tokens 再重复相加。无法读取用量时填 null、usage_observable=false，改用更短的 **2 轮 / 30 分钟** 上限；不得把未知当 0 或声称 token 限额已被强制执行。
- 超预算或恢复耗尽节点需要维护者明确批准新增额度并留历史。只加载当前节点及直接证据；已通过的全套测试只在相关代码变化、失败或新疑点出现后再跑。

## 写入节点状态

以下字段追加到 EXECUTION.md 的节点状态记录；实际执行后填写真实值，不能照抄示例冒充证据。

```json
{
  "model_policy": "docs/number1/MODEL-POLICY.md",
  "executions": [
    {
      "role": "worker",
      "model": "gpt-5.6-terra",
      "reasoning_effort": "medium",
      "round": 1,
      "tokens_used": null,
      "usage_observable": false,
      "approval_ref": null
    }
  ],
  "rounds_used": 1,
  "minutes_used": null,
  "tokens_used": null,
  "upgrade_requests": [],
  "approved_model_mapping": []
}
```

只有常规默认组合无需升级批准引用；high/Astra 或替代映射必须有维护者可核实的批准记录。记录 review 的实际模型/档位，与实现者共用节点预算。每批汇总记录各节点、协调者用量及剩余额度。

## 选型依据与复核

这是维护者批准的成本分级，不是官方对本项目的性能保证。官方模型资料将 [Terra](https://developers.openai.com/api/docs/models/gpt-5.6-terra) 定位为成本与能力平衡，将 [Sol](https://developers.openai.com/api/docs/models/gpt-5.6-sol) 定位为复杂专业工作；两者支持 medium/high。账号可用性以贡献者实际 Codex 环境为准，API 单价不能直接换算为订阅周额度。

当模型、effort、工具链或验收要求变化时，用一张代表性小单比较通过率、返工次数、总用量和时间，再由维护者调整本表；不自动追逐最新或最昂贵模型。
